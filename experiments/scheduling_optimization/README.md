# Scheduling Optimization — 요청 처리 순서 최적화 실험

## 이 실험의 목적

여러 질문이 같은 로컬 모델 서버를 사용할 때, **전체 평균 응답 시간의 이점을 유지하면서 오래 기다리는 Correction 요청의 지연을 줄일 수 있는지** 확인합니다.
Grading 실험은 질문을 하나씩 실제 실행했고, 이번 실험은 그때 얻은 **Full 처리 기록을 재생하는 시뮬레이션(trace replay)**입니다.
새 답변을 생성하거나 실제 질문 3,000개를 LLM 서버에 동시에 보내는 실험은 아닙니다.

## 완료 범위

- 실제 로컬 Full 질문 50개 기록을 사용한 시뮬레이션 완료.
- 원본 50개 중 서로 다른 Correction 사례는 5개.
- 부하 6개 × 도착 시드 5개 × 정책/강도 조합 6개 = 결과 180행.
- 각 조건에서 원본 기록을 반복 추출하여 요청 3,000개를 구성하고 앞 10%를 통계에서 제외.
- 완료 결과: `results/scheduling_optimization/20261101_101541/`
- 실제 동시 요청으로 정책을 제어하는 실행 검증, vLLM 통합, Correction 비율을 바꾸는 추가 실험은 하지 않았습니다.

## 비교 정책과 Aging의 의미

| 그래프 범례 | 의미 |
|---|---|
| `fifo_call` | 대기열에 들어온 LLM 호출 순서대로 처리 |
| `sjf_pred` | 질문 전체 예상 작업량이 짧은 순서대로 처리 |
| `srpt_est` | 질문의 예상 남은 작업량이 짧은 순서대로 처리 |
| `srpt_est + aging 0.1` | 기존 SRPT-est + 약한 대기 시간 우대 |
| `srpt_est + aging 0.5` | 기존 SRPT-est + 중간 대기 시간 우대 |
| `srpt_est + aging 1.0` | 기존 SRPT-est + 강한 대기 시간 우대 |

이번 코드의 우선순위 계산:

```text
우선순위 점수 = 예상 남은 모델 작업 시간 - α × 누적 대기 시간
```

**점수가 작을수록 먼저 처리합니다.** 오래 기다릴수록 점수가 내려가 긴 요청도 앞서 처리될 수 있습니다.
α(Aging 강도)는 한 조건 안에서 고정하고 조건별로 바꿔 비교합니다.
대기 시간은 이전 단계를 포함한 모델 서버 호출 대기 시간의 누적이며, 실제 계산 중인 시간은 제외합니다.
이미 실행 중인 LLM 호출은 끊지 않고, 다음 호출을 선택할 때 점수를 갱신합니다(호출 경계 스케줄링).

## 예상 남은 작업량과 Correction 상태

예측은 기존 기록의 입력 길이·처리 시간 등의 관계를 선형회귀로 계산합니다.
평가 중에는 남은 문서 평가와 이후 작업을 예상하고, Correction으로 분기하면 재작성·생성 등 남은 작업량 추정에 반영합니다.
이 **Correction 상태 반영은 팀원의 기존 SRPT-est에 이미 구현**돼 있습니다. 이번에 새로 추가한 핵심은 Aging입니다.

현재 구현은 기록을 먼저 읽어 모델을 만든 뒤 정책별로 비교합니다.
실제 서버에서 초기 FIFO 실행 → 기록 수집 → SRPT-est 자동 전환 또는 온라인 재학습하는 기능은 없습니다.
질문 단위 예측은 out-of-fold 방식이지만, 호출 비용 모델은 입력 기록 풀에 맞춰집니다. 완전히 새로운 데이터·하드웨어에서의 검증은 아닙니다.

## 실행 방법

프로젝트 최상위 폴더(`rag-system`)의 터미널에서 실행합니다.
아래는 재현 명령 안내이며, README를 여는 것만으로 실행되지는 않습니다.

### 1. 실제 측정 기록으로 정책 비교

```powershell
uv run python experiments/scheduling_optimization/run.py --profile "results/grading_optimization/grading 최종결과/profile.jsonl" --config experiments/scheduling_optimization/config.local.json
```

LLM을 새로 호출하지 않으므로 Ollama 서버나 OpenAI API 키를 켜둘 필요는 없습니다.
입력 파일은 앞서 완료한 로컬 Grading 실험의 Full 기록입니다. 현재 결과 폴더명은 `grading 최종결과`이며, 경로에 공백이 있어 따옴표로 감쌉니다.

### 2. 저장된 CSV로 그래프 생성

```powershell
uv run python experiments/scheduling_optimization/plot.py results/scheduling_optimization/20261101_101541
```

새 실행 결과를 그릴 때는 마지막 폴더명을 해당 실행의 `Saved:` 경로로 바꿉니다.

### 3. 코드 동작만 확인하는 합성 예제

```powershell
uv run python experiments/scheduling_optimization/run.py --demo
```

`--demo`는 가짜 작업으로 기능을 확인하는 모드입니다. 실제 PopQA 연구 결과로 사용하지 않습니다.

## 내가 직접 바꿀 실험 조건

본 실험에서는 **`config.local.json`**을 사용했습니다. 기본 `config.json`은 더 작은 예제 설정입니다.

| 설정 | 현재 값 | 의미 |
|---|---|---|
| `loads` | 0.3, 0.5, 0.7, 0.8, 0.9, 0.95 | 서버 처리 능력 대비 요청이 들어오는 부하 |
| `seeds` | 0, 1, 2, 3, 4 | 요청 추출·도착 간격을 바꿔 반복하는 시드 |
| `n_queries` | 3000 | 한 조건에서 재생할 요청 수. 서로 다른 질문 수는 아님 |
| `warmup_frac` | 0.1 | 초반 10% 요청을 통계에서 제외 |
| `aging_alphas` | 0.1, 0.5, 1.0 | 대기 시간을 우선순위에 반영하는 강도 |

부하 0.8은 GPU 사용률 80%가 아니라, 평균 모델 서버 작업량과 도착률로 정의한 부하입니다.
같은 부하/시드에서는 모든 정책에 동일한 요청 표본과 도착 시각을 사용합니다.
Aging 강도를 현재 결과에서 골라 설명하는 것은 탐색적 분석입니다. 일반적인 최적 강도를 주장하려면 별도 보정·평가 데이터가 필요합니다.

## 결과 파일과 측정값

결과는 `results/scheduling_optimization/실행날짜/`에 저장됩니다.

| 파일 | 내용 |
|---|---|
| `sim_results.csv` | 부하·시드·정책·Aging 강도별 수치 |
| `report.md` | 시드별 결과를 평균한 요약 표와 해석상 주의점 |
| `config.json` | 해당 실행에 사용한 설정 복사본 |
| `figures/` | 전체 지연, Correction 지연, 대기 시간, 처리량 그래프 6장 |

| CSV 열 | 의미 |
|---|---|
| `mean`, `p50`, `p95`, `p99` | 전체 요청의 응답 시간 평균·백분위수(초) |
| `mean_correct`, `p95_correct` | Correction 없이 완료한 요청의 응답 시간 |
| `mean_corrected`, `p95_corrected` | Correction이 발생한 요청의 **전체** 응답 시간. 보정 단계만의 시간이 아님 |
| `mean_gpu_wait` | 코드에서 물려받은 열 이름. 이번 입력 기준으로는 모델 서버 호출의 평균 대기 시간(초) |
| `mean_slowdown` | 부하가 없을 때에 비해 응답 시간이 늘어난 배율의 평균 |
| `throughput` | 정의된 관측 구간의 초당 완료 요청 수 |

그래프의 점은 도착 시드 5개의 평균이고, 오차 막대는 시드 간 표준편차입니다. 신뢰구간은 아닙니다.

## 이번 결과의 대표 예

부하 0.8, Aging 강도 0.5, 시드 5개 평균:

| 지표 | 기존 SRPT-est | Aging 추가 |
|---|---:|---:|
| 전체 평균 응답 시간 | 73.73초 | 77.69초 |
| Correction 평균 응답 시간 | 120.81초 | 86.65초 |
| Correction p95 응답 시간 | 405.74초 | 213.18초 |

전체 평균이 약 5.4% 증가하는 대신, Correction 평균은 28.3%, Correction p95는 47.5% 감소했습니다.
**현재 기록에서는 평균 지연과 긴 요청 보호 사이의 절충 효과가 관찰됐다**고 해석합니다. 전체 평균까지 모두 개선됐다는 뜻은 아닙니다.

## 한계와 공유 시 주의

- 원본은 질문 50개, 서로 다른 Correction 사례 5개입니다. 요청을 3,000개로 반복 추출해도 새로운 사례가 늘어나는 것은 아닙니다.
- 시드 반복은 요청 도착 상황의 변동을 확인하며, 원본 사례의 다양성이나 LLM 반복 측정을 대신하지 않습니다.
- 작업별 처리 시간과 답변을 고정한 시뮬레이션입니다. 답변 정확도·총 모델 작업량이 정책별로 새로 측정되거나 줄어드는 것은 아닙니다.
- GPU 사용률·메모리·전력을 이번 시뮬레이션에서 새로 측정하지 않았습니다. 입력 시간은 GPU·CPU 병용 로컬 서버 시간이며 순수 GPU 계산 시간이 아닙니다.
- 실제 동시 실행, 캐시·배칭·GPU 경쟁, vLLM 내부 스케줄링의 효과까지 검증한 결과는 아닙니다.
- `simulator.py`는 팀원의 `experiments/correction_scheduling/scheduling.py`를 실험 폴더 안에 확장한 코드입니다. 팀원 원본과 공통 `src/rag/`, `configs/base.yaml`은 변경하지 않았습니다.
- `verify.py`는 Aging 강도 0에서 기존 정책과 결과가 일치하는지 확인합니다.
- 코드는 실험별 브랜치로 공유하고 데이터·결과·API 키는 커밋하지 않습니다. 그래프 생성에는 matplotlib가 필요합니다.
